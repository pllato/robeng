# Pixel English — развёртывание и эксплуатация сервера

Документ для агента, который отвечает за сервер. Разработка игрового контента
(объекты, уроки, механики) ведётся отдельно; сюда приходят готовые файлы.

**Разделение зон:**

| зона | кто ведёт | что делает |
|---|---|---|
| Игровой код и контент | другой агент | правит `server.js`, `public/index.html`, уроки |
| Сервер и выкладка | **ты** | ставит, обновляет, следит, чинит |

Ты не меняешь игровую логику. Если для работы сервера нужна правка в коде игры —
опиши проблему и передай её тому, кто ведёт разработку.

---

## 1. Что это за приложение

Многопользовательский пиксельный мир для обучения детей 5–11 лет английскому.
Дети ходят по общему миру, выращивают «грядки слов» и произносят слова в микрофон.

**Технически:**

- Один процесс Node.js. Без Docker, без базы данных, без внешних сервисов.
- HTTP отдаёт статику из `public/`, на том же порту живёт WebSocket (библиотека `ws`).
- Всё состояние мира — в памяти процесса. На диск пишется только `data/db.json`
  (аккаунты, сады, классы) — с задержкой 800 мс после изменения и по `SIGINT`.
- Голос между детьми идёт по WebRTC **напрямую, минуя сервер**. Через сервер
  проходят только служебные сообщения установки связи.

**Состав:**

```
server.js            единственный серверный файл (~47 КБ)
package.json         одна рабочая зависимость: ws
public/index.html    вся игра целиком, один файл (~175 КБ)
public/lessons/      100 уроков + index.json (420 КБ)
data/db.json         состояние: аккаунты, сады, классы (растёт медленно)
```

`playwright` лежит в `devDependencies` — на сервер он не ставится.
Устанавливай строго `npm install --omit=dev`.

## 2. Требования к серверу

Измерено нагрузочным тестом (детали в разделе 8), не оценка:

| нагрузка | процессор | память |
|---|---|---|
| 10 игроков в одной комнате | 1.3% ядра | 74 МБ |
| 30 игроков в одной комнате | 9.8% ядра | 74 МБ |
| 60 игроков в одной комнате | 17% ядра | 75 МБ |

**Достаточно 2 vCPU и 2–4 ГБ памяти.** Запас пятикратный.
Память от числа игроков практически не растёт: мир хранится один раз.

Трафик: около 9 ГБ в месяц при 50 учениках по три занятия в неделю.
Любой тариф это покрывает.

**Образ:** Debian 13 или Ubuntu 24.04 LTS — `server-setup.sh` работает на обоих.
На этом сервере стоит Debian 13, переустанавливать его не нужно.

### Какой хостинг подходит

Провайдер значения не имеет — Hetzner, любой европейский или казахстанский.
Значение имеет **тип** хостинга:

| тип | подходит | почему |
|---|---|---|
| **VPS / VDS / выделенный сервер** с root и Ubuntu | **да** | всё в этом документе работает без изменений |
| Виртуальный хостинг (cPanel, ISPmanager, «сайт на PHP») | нет | нужен постоянно живущий процесс Node и WebSocket — там их нет |
| Serverless / PaaS (Vercel, Netlify, облачные функции) | нет | состояние мира живёт в памяти процесса, функции его теряют между вызовами |

**Что требовать у хостера при заказе:**

1. Root-доступ по SSH и чистая Debian 13 или Ubuntu 24.04 LTS (не готовая «панель управления»).
2. Публичный IPv4 и возможность направить на него `A`-запись домена.
3. Открытые входящие 22, 80, 443 и **отсутствие обязательного прокси/WAF провайдера**
   перед сайтом — WebSocket через такие прокси часто не проходит.
4. Право поставить свои пакеты (Node, Caddy) — то есть не «управляемый» тариф.
5. Резервное копирование или снапшоты на стороне хостера — приятно, но не замена
   ежедневной копии `db.json` из раздела 7.

Если провайдер предлагает готовый образ с Node — не бери, `server-setup.sh`
поставит нужную версию сам.

### Локация

Ученики в Алматы. Задержка до Германии — примерно 90–120 мс, до Казахстана —
5–20 мс. Для игры это не критично: мир не требует быстрой реакции, движение
рассылается раз в 120 мс. На **голосовой связи** разница заметнее, но голос
идёт напрямую между детьми, минуя сервер, — расположение сервера на него
почти не влияет.

**Отдельно, и это важнее скорости:** в `data/db.json` лежат имена детей и
телефоны родителей. Законодательство Казахстана о персональных данных требует
хранить персональные данные граждан на территории страны. Это вопрос к
владельцу и, если нужно, к юристу — но если ответ «хранить в РК», то выбор
хостера предрешён: казахстанский VPS (ps.kz, hoster.kz и подобные).
Технически для развёртывания ничего не меняется.

## 3. Первичная установка

**Данные этого сервера:**

| | |
|---|---|
| Хостер | netcup, тариф VPS 500 G12 (2 vCPU, 4 ГБ, 128 ГБ NVMe) |
| Локация | Нюрнберг, Германия |
| IPv4 | `89.58.11.76` |
| IPv6 | сеть `2a03:4000:5f:827::/64` — не настроена, AAAA-запись не заводим |
| Домен | `pixel.elc-kids.kz` |
| Система | **Debian 13** (образ netcup по умолчанию), доступ root по SSH |
| Панель хостера | servercontrolpanel.de (образы, перезагрузка, консоль) |


Скрипт `server-setup.sh` делает всё сам. Запускается **один раз** на свежем
сервере под root:

```bash
scp server-setup.sh root@<IP>:/root/
ssh root@<IP> 'bash server-setup.sh pixel.elc-kids.kz'
```

Что он делает по шагам:

1. Проверяет Node.js: ставит 22 из NodeSource, только если в системе его нет
   или версия ниже 20 (в Debian 13 штатный Node 20 подходит, установка пропускается).
2. Ставит Caddy — он получает и продлевает сертификат Let's Encrypt сам.
3. Заводит системного пользователя `mineenglish`, папку `/opt/mineenglish`.
4. Создаёт `/etc/mineenglish.env` (права 600) со случайным `ADMIN_PIN`,
   `PUBLIC=1`, `PORT=8642`, и systemd-юнит `mineenglish.service`.
5. Пишет `Caddyfile`: домен → `reverse_proxy 127.0.0.1:8642`.
6. Включает ufw: открыты только 22, 80, 443.

**Пароль владельца печатается один раз в конце.** Сохрани его в менеджер паролей
и передай владельцу. Повторно он не показывается, но лежит в `/etc/mineenglish.env`.

**Предусловие:** DNS-запись `A pixel.elc-kids.kz → <IP>` должна существовать
**до** запуска, иначе Caddy не выпустит сертификат. Проверь:
`dig +short pixel.elc-kids.kz` должен вернуть IP сервера.

## 4. Выкладка обновлений

Игровые файлы приходят от разработки. Кладёшь их в рабочую копию и запускаешь:

```bash
./deploy.sh
```

Скрипт:

1. Проверяет `ssh` и `node --check server.js` — битый файл на сервер не поедет.
2. Заливает `server.js`, `package.json`, `public/` через rsync.
3. `npm install --omit=dev`, права на `mineenglish`.
4. **Переносит `data/db.json` только если на сервере его ещё нет.** Существующую
   базу никогда не перезаписывает.
5. `systemctl restart mineenglish`, ждёт, проверяет `systemctl is-active`.
6. Сверяет сборку: `curl 127.0.0.1:8642/version` против `BUILD` в файле.
   **Если версии не совпали — выкладка не удалась**, разбирайся, не считай успехом.

При неудачном рестарте выводит `journalctl -u mineenglish -n 15`.

### Ручная выкладка, если скрипта нет под рукой

```bash
rsync -az server.js package.json root@<IP>:/opt/mineenglish/
rsync -az --delete public/ root@<IP>:/opt/mineenglish/public/
ssh root@<IP> 'cd /opt/mineenglish && npm install --omit=dev \
  && chown -R mineenglish:mineenglish . && systemctl restart mineenglish'
```

## 5. Версии — как понять, что развёрнуто

В `server.js` и в `public/index.html` есть константа `BUILD` вида `2026-09-04-2`.
Они **должны совпадать между собой** — иначе обновилась только половина.

- `GET /version` → `{"build":"...","started":"...","pid":...}`
- В самой игре: версия видна на первом экране под кнопкой «Войти в школу».
  При расхождении там пишется «обновилась только половина».

Это главный инструмент диагностики. Раньше основной причиной «ничего не
изменилось» была именно выкладка старого файла.

## 6. Безопасность: что нельзя ломать

Приложение работает с **персональными данными детей и родителей** — имена,
телефоны в заявках. Всё это в `data/db.json` в открытом виде.

**Требования, которые нельзя ослаблять:**

1. **`PUBLIC=1` обязателен в интернете.** При нём сервер отказывается стартовать,
   если у владельца стандартный PIN. Не убирай эту переменную.
2. **`ADMIN_PIN` — длинный.** Он переустанавливает пароль владельца при каждом
   старте. Хранится в `/etc/mineenglish.env` с правами 600.
   Пароль, которым пользовались на временном туннеле до переезда, считается
   раскрытым — на сервере его не используй. `server-setup.sh` генерирует новый сам.
3. **Не логируй телефоны.** В коде это уже убрано, не возвращай.
4. **Не открывай порт 8642 наружу.** Только через Caddy на 443.
5. **Не выкладывай `data/db.json`** в репозитории, чаты, логи.

Встроенная защита от перебора PIN: 5 неудачных попыток → пауза, растёт до часа.
Считается по паре «адрес + имя». Вход по сохранённому токену не затронут.

Учительский PIN — минимум 6 цифр, ученический — 4 (у ученика в аккаунте только
звёзды и сад).

## 7. Эксплуатация

### Проверка состояния

```bash
systemctl status mineenglish
journalctl -u mineenglish -n 50 --no-pager
curl -s localhost:8642/version
```

### Резервные копии

`data/db.json` — единственное, что нельзя потерять. Настрой ежедневную копию:

```bash
# /etc/cron.daily/mineenglish-backup
#!/bin/sh
d=/opt/mineenglish/backups
mkdir -p "$d"
cp /opt/mineenglish/data/db.json "$d/db-$(date +%F).json"
find "$d" -name 'db-*.json' -mtime +30 -delete
```

Файл небольшой (сотни килобайт), 30 копий ничего не весят.
Хорошо бы дополнительно выгружать копию за пределы сервера.

### Перезапуск и откат

```bash
systemctl restart mineenglish        # перезапуск
systemctl stop mineenglish           # остановить на время работ
```

Откат: положить прежние `server.js` и `public/index.html`, перезапустить.
Держи предыдущую версию под рукой перед каждой выкладкой.

### Обновления системы

`unattended-upgrades` для security-обновлений — включи. Перезагрузку сервера
планируй вне занятий: игра поднимется сама (`Restart=always`), но дети,
игравшие в этот момент, вылетят и потеряют несохранённый прогресс за последние
секунды.

## 8. Как измерялась нагрузка

Чтобы можно было повторить и сравнить после изменений.

Метод: N клиентов на `ws`, каждый шлёт `{"t":"move",...}` каждые 120 мс —
ровно как настоящий клиент. Сервер рассылает каждое движение всем остальным
в той же комнате, поэтому нагрузка внутри комнаты растёт квадратично.
Процессор и память снимались снаружи из `/proc/<pid>/`.

Результаты — в разделе 2. Отдельно: **30 учеников открыли игру одновременно
за 94 мс**, процессор 0.4%. Один вход — 186 КБ (страница 172 КБ + каталог 14 КБ).

Важно: шесть классов по 10 человек дают в разы меньше трафика, чем 60 человек
в одной комнате. Занятия идут отдельными мирами, так что реальная нагрузка
ближе к нижней строке таблицы.

## 9. Известное ограничение: голос

В клиенте настроен только STUN (`stun.l.google.com:19302`), TURN нет.

Следствие: у части детей голосовая связь **не установится** — обычно это
мобильный интернет некоторых операторов и сети со строгим NAT. Дома по Wi-Fi
чаще всего работает.

Если жалоб окажется много — нужен TURN-сервер (coturn) на этой же машине.
Тогда голос пойдёт через сервер: примерно 50 кбит/с на говорящего,
группа из восьми даст около 3 Мбит/с в пике. Сервер это выдержит,
но добавление TURN требует правки клиента — это к разработке.

## 10. Что делать, если не работает

| симптом | куда смотреть |
|---|---|
| Сайт не открывается | `systemctl status caddy`, `journalctl -u caddy -n 50` |
| Сертификат не выпустился | DNS-запись, порт 80 открыт, `dig +short <домен>` |
| Открывается, но не входит в мир | WebSocket: в Caddy `reverse_proxy` поддерживает его сам, отдельной настройки не нужно. Смотри `journalctl -u mineenglish` |
| «Сервер не подтвердил действие» у игрока | сервер отвечает на каждый отказ текстом причины — он придёт игроку и попадёт в лог |
| Версия в игре старая | `curl localhost:8642/version` против `BUILD` в файлах; выкладка не доехала |
| Игра падает и перезапускается | `journalctl -u mineenglish -n 100`, ищи стек. Передай текст разработке |
| Не хватает памяти | не должно случаться при 75 МБ; если растёт со временем — это утечка, сообщи разработке с графиком |

Быстрая проверка живости:

```bash
curl -sf https://pixel.elc-kids.kz/version || echo "СЕРВЕР НЕ ОТВЕЧАЕТ"
```

Стоит завести внешний мониторинг (UptimeRobot или аналог) на этот адрес.

## 11. Чего делать не нужно

- Не ставь Docker, PM2, nginx — systemd и Caddy закрывают задачу.
- Не переноси состояние в PostgreSQL/Redis. Игра рассчитана на один процесс
  и файл; смена хранилища — это переписывание, а не эксплуатация.
- Не запускай несколько экземпляров за балансировщиком: состояние мира в памяти,
  игроки окажутся в разных мирах.
- Не правь `public/index.html` и `server.js` на сервере вручную — следующая
  выкладка затрёт правку, и никто не поймёт, почему поведение менялось.
